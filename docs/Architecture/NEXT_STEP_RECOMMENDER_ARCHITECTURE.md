# Next-Step Recommender Architecture

> **"Smart Next Steps"** — ephemeral, token-light follow-up suggestions shown after every turn. Designed around three properties: **action-aware & tool-grounded**, **token-light by default**, and **anti-fatigue / optional**. Default configuration spends **zero extra LLM tokens**.

## 1. System Overview

After a turn completes, the recommender proposes a small, capped set of next steps the user might take — either **actions** ("Chart this", "Pin to dashboard", "Build a flow") or **follow-up questions** ("Break this down by region"). Suggestions are rendered as clickable chips in a dock above the composer; clicking one submits it as the next turn.

The recommender is:

- **Ephemeral** — suggestions attach only to the latest turn, are never persisted to chat history, and vanish on the next submit or session switch.
- **Token-light** — the two default tiers (action chips + RAG follow-ups) spend zero extra LLM tokens. The LLM tier is strictly opt-in.
- **Optional at three levels** — global admin gate, per-profile config, per-user mute.
- **Profile-context-aware** — re-binds to the effective profile on every turn (honors `@TAG` overrides and reverts).
- **Defensive** — any failure is swallowed; a recommender error can never break a turn.

## 2. Design Goals & Market Position

The market (ChatGPT, Gemini, Perplexity, Copilot) has converged on showing **3–5 suggested questions** after an answer, usually generated by a **secondary LLM call** (extra tokens/latency per turn). Three gaps remain unfilled, and Uderia's primitives (component catalog + RAG champion cases + per-profile config) let it fill all three:

| Market gap | Uderia's answer |
|---|---|
| Suggests *questions* only, not *actions* | **Tier A action chips** grounded in the profile's enabled component manifests |
| Suggestions can be dead-ends (propose things the product can't do) | Chips are gated by the **exact same enablement truth as the profile editor** — every chip maps to a genuinely-enabled capability |
| Extra LLM call per turn (cost/latency) | **Tiers A+B are free** (deterministic + retrieval); LLM is opt-in, capped, async |
| Engagement-baiting / suggestion fatigue | Hard cap, confidence-gated, suppressed when empty, auto-clears on next turn, fully disableable |

## 5. The Cost Ladder (Three Tiers)

Suggestions are assembled cheapest-first, capped at `maxSuggestions`. Action chips lead (highest value, free); follow-ups fill remaining slots; the LLM tier fills any still-empty slots only if opted in.

| Tier | Key | Source | Token cost | Default |
|------|-----|--------|------------|---------|
| **A** | `action` | Enabled component manifests + turn result shape | **0** | ON |
| **B** | `followup` | RAG champion-case retrieval seeded with the just-asked query | **0 generation** | ON |
| **C** | `llm` | Compact, history-disabled LLM call | small (per turn) | **OFF** |

Default config = A + B → **zero added tokens per turn**.

## 6. Backend Integration Seam

The recommender hooks into **one** place: `execution_service.run_agent_execution`. This is the true convergence point for every profile type — both the genie coordinator path (`CoordinateEngine.execute_genie`) and the `PlanExecutor` path (Ideate / Focus / Optimize / Conversation engines) set `final_result_payload` here.

> **Important:** the five engines each emit their *own* `final_answer` event; they do **not** all converge on `executor._format_and_yield_final_answer`. The only shared seam is `run_agent_execution`. Do not attempt to hook the recommender per-engine.

```python
# execution_service.py — after the engine completes, before the except
if (not _is_genie_slave
        and isinstance(final_result_payload, dict)
        and final_result_payload.get("final_answer")):
    from trusted_data_agent.agent.recommender import build_and_emit_suggestions
    await build_and_emit_suggestions(
        user_uuid=user_uuid, session_id=session_id, user_input=user_input,
        profile=active_profile,                       # ← effective profile for THIS turn
        final_payload=final_result_payload,
        turn_id=final_result_payload.get("turn_id"),
        event_handler=event_handler,
    )
```

- **`_is_genie_slave`** (already computed at the top of `run_agent_execution`) skips nested genie *slave* sub-turns — their session is never the one the user views, so suggestions would be wasted.
- `build_and_emit_suggestions` **never raises** — it wraps everything in `try/except` and simply emits nothing on failure.

## 7. Tier A — Action Chips & Enablement Governance

> **One act, one place (Oct 2026).** When the answer itself carries "Pin to dashboard" — a data row's table or a pinnable component row (manifest `answer_surface.pin`) — `derive_render_flags` sets `has_direct_pin` and Tier A offers **no** "Pin to dashboard" chip: asking the agent to pin would be the same act at the cost of a turn. Answers with nothing pinnable to click keep the chip. A stashed rebind descriptor without the key reads `False` (the chip is offered, as before).

Tier A maps the turn's result shape to chips drawn from a fixed template table, but **only** for components that are genuinely enabled for the profile.

**Result-shape rules** (`_result_shape` inspects `collected_data`):

| Condition | Chips offered (if component enabled) |
|---|---|
| Tabular result (any list-of-dicts in `collected_data`) | `chart` (unless a chart was already rendered), `dashboard`, `scheduler`, `flow` |
| A chart already rendered this turn, no raw table | `dashboard` |
| Code in the answer (` ``` ` / `<pre`) | `canvas` (unless canvas already rendered) |
| A knowledge graph already drawn | `knowledge_graph` (expand) |
| The turn stopped early because its budget ran out (`stopped_early`, from `final_payload.budget.exhausted`) | `action:continue` — **Continue where it stopped**, offered FIRST and independent of any component (see [ENGINE_MODULARIZATION_ARCHITECTURE.md](ENGINE_MODULARIZATION_ARCHITECTURE.md) → The Visible Budget) |

**Enablement truth — `_component_enabled_for_profile`.** This mirrors the profile editor's `profile_enabled` derivation (`GET /v1/profiles/<id>/components`) **exactly**:

1. **Global admin gate / per-user override wins** — `is_component_available(comp_id, user_uuid)` (checks `component_settings.disabled_components` + `user_component_settings`). If unavailable → never offered.
2. else **explicit** `componentConfig[comp].enabled`.
3. else **manifest default for this profile type** — `profile_type in comp.profile_defaults.enabled_for`.

> ⚠ **Do NOT gate Tier A on `ComponentManager.get_active_components`.** That helper defaults an *absent* `componentConfig` entry to `enabled=True` and ignores global/user governance — which leaked disabled components into suggestions (the original bug). The recommender deliberately re-implements the editor's truth instead so a chip is offered **iff** the user actually has that component on.

Because chips submit a natural-language prompt (e.g. "Create a chart that best visualizes the results above"), an enabled component guarantees the corresponding tool is available at execution — no dead-ends.

## 8. Tier B — RAG Follow-up Retrieval

Tier B reuses the same champion-case store that powers input autocomplete, but seeds retrieval with the **just-completed** query — so suggestions are "what people usually ask *next*" rather than "what people ask first".

- Calls `rag_retriever.retrieve_examples(query=<asked>, repository_type="planner", …)`.
- Honors the profile's `autocompleteCollections` scope (`["*"]` = all, `[]` = Tier B disabled).
- **The access context is mandatory, and the seam is bounded (Aug 2026).** Retrieval runs with a `RAGAccessContext` for the requesting user (imported from `agent/rag_access_context.py` — it does NOT live in `rag_retriever.py`; a wrong-module import swallowed by a bare `except` once left every turn running `rag_context=None`). `rag_context=None` means *no scope*: `retrieve_examples` then scans EVERY loaded planner collection — every user's private champion cases become suggestion candidates, and on an instance with hundreds of per-user default repositories that scan cost ~27 s per turn **on the event loop** (the answer's assurance dial waited on it; every other session stalled behind it). If the context cannot be built, Tier B returns `[]` — never an unscoped scan. The call is wrapped in `asyncio.wait_for(APP_CONFIG.RECOMMENDER_TIER_B_TIMEOUT_SECONDS`, default 5 s) because this seam is awaited in the turn's critical path (the chips ride the same event stream as the answer).
- **Retrieval cost is independent of collection count.** `RAGRetriever.retrieve_examples` embeds the query ONCE per embedding model and hands ChromaDB the vector (`query_embeddings`); `collection.query(query_texts=…)` re-embeds inside every collection call (~0.1 s each on CPU). The encode and each HNSW query run via `asyncio.to_thread` — ChromaDB is synchronous, and a blocked loop is a server-wide stall. Gate: `test/test_rag_retrieve_embed_once.py` (embed-once · off-loop · scoped · encoder-failure fallback · no sync `collection.query` in the function) + `test_recommender.py::test_tier_b_access_scope` (context always passed · fail closed · bounded). Both in `trust_battery.sh`.
- Filters by `recommenderConfig.relevanceThreshold`.
- **Dedupe is tag-stripped + normalized**: a candidate is dropped if, after removing a leading `@TAG` and normalizing case/punctuation/whitespace, it equals the asked query or another candidate. (Champion cases sometimes store the `@TAG` prefix — it is stripped for both comparison and display, so a chip never shows `@OPTIM …`.)
- Graceful empty on missing retriever / disabled collections.

## 9. Tier C — Opt-in LLM Enrichment

Tier C runs **only** when both `"llm" ∈ tiers` and `llmEnrichment: true`, and **only** to fill slots still empty after A+B (≤ `maxSuggestions`).

- Builds an LLM client from the profile's `llmConfigurationId` (provider/model + merged credentials). No config → silent no-op.
- Compact prompt: the asked question + an 800-char answer excerpt; **`disabled_history=True`** (no chat history → small input); asks for "at most N short follow-up questions as a JSON array".
- Runs **after** `final_answer` has already streamed, so it never delays the response.
- Parsed with `robust_json_parse`; deduped against the asked query and existing chips.

Cost is bounded by design (tiny input, short output, leftover-slots-only). It is OFF by default because it is the only tier that spends tokens.

**Full observability & accounting — mirrors Session Name Generation.** Because Tier C spends real tokens, the call is a first-class, fully-instrumented LLM call (`_run_tier_c_with_accounting` + `_record_tier_c_usage`), exactly like the post-turn session-name call:

| Concern | Mechanism |
|---|---|
| **Live Status panel** | Emits a **single** `next_step_generation_complete` step ("Smart Next Steps Generated") rendered as a clean key/value card — **Suggestions / Tokens / Cost** — by `_renderNextStepCompleteDetails` (`ui.js`), matching the Session Name card exactly. Wired into all three render dispatchers (`_renderStandardStep`, `_renderGenieStep`, `_renderConversationAgentStep`) so it renders for every profile type, live and on reload. No separate "start" card (one event is sufficient). |
| **Cost engine** | `CostManager.calculate_cost(provider, model, in, out)`; the cost flows to the live counter through **one** `token_update` event with a stable `call_id = "next_step_recommender"`. The frontend cost ledger is idempotent per `call_id`, so the step event stays display-only and never double-counts. Reload cost: `_getTurnCost` includes `next_step_generation_complete`. |
| **Live token counters** | The `token_update` carries `statement_*` (this call), `turn_*` (existing turn total + Tier C), and `total_*` (refreshed session totals). |
| **Last-statement (reload)** | Tier C runs *after* session-name generation, so it is the chronologically-last LLM call. `_getLastStatementTokens` reverse-scans `system_events` for `['session_name_generation_complete', 'next_step_generation_complete']` and returns the later one, so the "Last Statement" KPI shows the Tier C call on reload (not session-name). |
| **Session history** | `update_token_count` (session cumulative) + `update_turn_token_counts` (turn totals → recomputes `turn_cost`/`session_cost_usd`) + `append_system_events_to_turn` (persists the completion step so it re-renders on reload). |
| **Consumption / billing** | `ConsumptionManager.update_turn_tokens` (same ledger extensions use). Tier C runs *after* the turn is saved+billed, so — like post-turn extensions — it must bill explicitly (session-name runs *before* the save, so it's billed implicitly via the turn total). |

Provider/model come from the call's returned usage (fallback to the turn's). The entire accounting block is wrapped so a failure degrades to "chips delivered, accounting skipped" without breaking the turn. **Validated across all 5 engine branches** (optimize/ideate/focus/conversation/genie) — each emits `turn_id` on its `final_answer`, so turn-level persistence lands for every profile type.

## 10. SSE Event Contract

Emitted via the turn's `event_handler` as a `notification` event:

```json
event: notification
data: {
  "type": "next_step_suggestions",
  "payload": {
    "session_id": "…",
    "turn_id": 7,
    "profile_id": "profile-…",
    "rebindable": true,
    "items": [
      { "id": "action:chart", "kind": "action",   "label": "Chart this",
        "prompt": "Create a chart that best visualizes the results above.", "icon": "chart" },
      { "id": "followup:42",  "kind": "followup", "label": "Break this down by region",
        "prompt": "Break this down by region", "icon": "followup" }
    ]
  }
}
```

- `kind` ∈ `{action, followup}` (drives styling; action chips lead visually).
- `prompt` is what gets submitted on click; `label` is the chip text.
- `icon` is a key into the frontend's monochrome SVG map.
- `profile_id` is the effective profile that produced these chips; `rebindable` is `true` whenever the turn stashed a rebind context (see §12a). Together they let the frontend re-filter the chips when the composer's `@TAG` changes.
- Emitted **after** `final_answer` (FIFO async generator → ordering preserved). Emitted **even when `items` is empty** if the turn is `rebindable` (so a later profile switch can surface chips for the same result); a non-rebindable empty result stays silent.

**Tier C also emits (only when the opt-in LLM call runs):**

| Event | Purpose |
|---|---|
| `next_step_generation_complete` | Single Live Status step "Smart Next Steps Generated"; `details` carries `input_tokens`, `output_tokens`, `cost_usd`, `suggestion_count` (also the reload cost/last-statement source). Rendered as a clean Suggestions/Tokens/Cost card. |
| `token_update` (`call_id: "next_step_recommender"`) | Rolls tokens/cost into the live turn/session counters (idempotent per `call_id`) |

## 11. Frontend: The Ephemeral Dock

The dock (`#next-step-dock`) lives **above the composer, outside `#chat-log`**. This placement is the core of the conflict-free design:

| Risk avoided | Why |
|---|---|
| Stale chips on session switch | Not inside `#chat-log`, so never captured by `sessionUiCache.chatHTML` |
| Polluting saved chat history | Never written to `chat_object` / `session_history` |
| Markdown re-parse / MutationObserver churn | Outside the observed chat log |

**Layout — chrome-free, full-width single row.** The dock renders **only the chips** (no header label, no dismiss control — the dock auto-clears on the next turn, so neither earns the vertical estate). Although it sits inside the centered `max-w-5xl` composer column, the chips **break out to the full chat-pane width** so they stay on **one row**: `#chat-footer` is a CSS query container, so the dock is `width: 100cqw` (the pane's content width — it shrinks with the resource panel; no `100vw` hacks) with a negative margin that re-centres the breakout on the column. The row is `flex-wrap: nowrap` + `justify-content: safe center` (centred when it fits, start-aligned without clipping when it overflows) + `overflow-x: auto`, with an edge-fade `mask-image` that only shows when the row reaches its edges — a free "scrollable →" affordance. All CSS/JS → browser-reload only.

**State & lifecycle** (`nextStepHandler.js` + `state.nextStepSuggestions` keyed by session id):

- **Receive** (`eventHandlers.js` notification handler): session-guarded — if `payload.session_id === state.currentSessionId`, store + render; otherwise stash for switch-back only.
- **Render** (`renderDock`): no-op/hide unless the session is the one being viewed and the per-user toggle is on.
- **Clear on new turn** (`handleChatSubmit`): a new submit supersedes the previous turn's suggestions.
- **Session switch** (`sessionManagement.js`): re-renders from state on both the active-stream restore path and the idle load path — so concurrent sessions stay isolated by construction.
- **Click** fills the composer and dispatches the chat-form `submit` (the existing path); uses `click` (not `mousedown`) so keyboard activation works.

## 12. Profile Context Awareness

The recommender binds to the **effective profile for each turn**, recomputed inside `run_agent_execution`:

```python
profile_id_to_use = profile_override_id or default_profile_id   # override-first
active_profile     = <profile matching profile_id_to_use>
```

Consequences (all automatic, no caching):

| User action | Next turn's suggestions |
|---|---|
| Adds an `@TAG` override | Reflect the **override** profile's `componentConfig` + `recommenderConfig` |
| Drops the override | Auto-revert to the **default** profile |
| Changes the default profile | Use the new default (reads `get_default_profile_id` fresh, ignores stale session `profile_id`) |
| Deletes the active/override profile | Fall back to default (deleted profile won't resolve) |

**Proof** — same query + identical tabular result, only the profile varies:

```
OPTIM (chart off, dashboard on)          → ['Pin to dashboard']
FOCUS (chart on, scheduler on, …)        → ['Chart this','Pin to dashboard','Schedule this','Build a flow']
IDEAT (chart off, dashboard on)          → ['Pin to dashboard']
COORD (chart on, scheduler on, …)        → ['Chart this','Pin to dashboard','Schedule this','Build a flow']
```

The chip set tracks each profile's `componentConfig` exactly.

## 12a. Profile Rebind (live re-filter on `@TAG` change)

§12 makes suggestions track the effective profile, but only **at turn-completion time**. The rebind layer extends that to **composer-edit time**: when you add or remove an `@TAG` override (or pick a profile from the selector) *without* running a new turn, the chips re-filter to the selected profile's class against the **same last result** — with **zero tokens** and no new turn.

**Why this is sound.** Tier A chips are a pure function of `(result shape) × (selected profile's enabled components)`. Switching the override changes only the component filter; the result is fixed. So the chips can be recomputed for the new profile from a tiny stored descriptor — no `collected_data` or HTML needed.

**Mechanism:**

1. **Stash (emit time).** `build_and_emit_suggestions` computes `derive_render_flags(final_payload)` — a compact `{tabular, rows, has_chart, has_canvas, has_code, has_kg}` descriptor — and stamps `{query: <tag-stripped asked>, flags}` onto the turn via `session_manager.set_turn_rebind_context`. Stashed for **every** rebindable turn, independent of whether the emitting profile produced chips.
2. **Rebuild (rebind endpoint).** `POST /v1/sessions/<id>/next-step-rebind {profile_id, turn_id?}` loads the stashed context, resolves the profile, and calls `recommender.build_rebind_suggestions(profile, query, flags)` → the free **A+B** set for that profile. **Tier C is never run here** — a profile toggle must not fire an LLM call. Always degrades to `{items: []}` rather than erroring.
3. **React (composer).** A debounced `scheduleProfileRebind()` fires from the composer `input` listener, the badge-remove handlers, and the profile selector. `applyEffectiveProfile()` resolves the composer's effective profile (`getEffectiveProfileId`, mirroring the backend's override-first rule), and:
   - **cache hit** (`state.nextStepCache[sid][profileId]`) → render instantly;
   - **miss** → fetch the rebind endpoint, cache the result (even when empty, so toggling never re-fetches), and render if still the effective profile.

**Per-profile caching** (`state.nextStepCache`, keyed `session → profileId`) is exactly the artifact §1's session-keyed store is not: it makes flipping `@FOCUS` on and off re-show each profile's chips with no network round-trip after the first. The emitting profile's set is seeded into the cache from the SSE payload, so toggling **back** to it (which preserves any Tier C chips) is also instant.

**Lifecycle:** `state.nextStepRebind[sid]` marks a session as having a rebindable turn. It (and the cache) are wiped by `clearDock` on a **new submit** or **dismiss** — a new turn re-stashes and re-seeds. Session **switch-away** does **not** clear them (only re-renders), so concurrent sessions keep independent rebind state.

| User action (no new turn) | Dock result |
|---|---|
| Type `@FOCUS ` over an Optimize turn's chips | Re-filters to FOCUS's class (chart/scheduler/flow if enabled) |
| Delete the `@FOCUS` override | Reverts to the default profile's chips (cache hit → instant) |
| Pick a profile from the `@` selector | Re-filters to that profile |
| Toggle back to the turn's own profile | Restores the original emitted set (Tier C chips intact) |

## 13. Governance Model (Three Levels)

| Level | Control | Where |
|---|---|---|
| **Global (admin)** | `APP_CONFIG.RECOMMENDER_ENABLED` — when `False`, no profile emits suggestions | `core/config.py` |
| **Per-profile** | `recommenderConfig` block (`enabled`, `tiers`, `maxSuggestions`, `relevanceThreshold`, `llmEnrichment`) | Profile editor → "Smart Next Steps" card |
| **Per-user** | localStorage mute (`tda_next_step_enabled`); the dock also auto-clears on the next turn | `nextStepHandler.js` |

Tier A additionally inherits **component governance** (global disable list + per-user `user_component_settings`) via `is_component_available`.

## 14. Configuration Reference

`recommenderConfig` on a profile (absent block → defaults: A+B on, capped at 4):

```json
"recommenderConfig": {
  "enabled": true,
  "tiers": ["action", "followup"],   // add "llm" to opt into Tier C
  "maxSuggestions": 4,
  "relevanceThreshold": 0.65,        // Tier B similarity floor (0..1)
  "llmEnrichment": false             // Tier C master switch (also needs "llm" in tiers)
}
```

**Enabling Tier C:** Profile editor → **Smart Next Steps** card → tick **"LLM enrichment"**. The save handler sets both `"llm" ∈ tiers` and `llmEnrichment: true` together (Tier C requires both). It fills only leftover slots after A+B, so raise `maxSuggestions` if you want it to contribute more often.

Defaults live in `DEFAULT_RECOMMENDER_CONFIG` (`recommender.py`). Profiles persist arbitrary keys (`config_manager.update_profile` does `profile.update(updates)` — no whitelist), so no schema migration is needed.

Global (`core/config.py`, admin-level, not per-profile):

| Key | Default | Meaning |
|---|---|---|
| `RECOMMENDER_ENABLED` | `True` | Master gate — `False` means no profile can emit suggestions |
| `RECOMMENDER_TIER_B_TIMEOUT_SECONDS` | `5.0` | Upper bound on the Tier B champion-case retrieval. The seam is awaited in the turn's critical path (before the online-eval dispatch that settles the assurance dial), so a slow store yields no follow-ups instead of holding the turn |

## 15. Visual & Accessibility Standards

- **Theme-aware** — all colors use CSS variables (`--card-bg`, `--text-primary`, `--text-muted`, `--border-primary`, `--hover-bg-strong`, `--teradata-orange`), verified in both dark and light themes.
- **Monochrome industrial icons** — single-`currentColor` inline SVGs (chart, dashboard, flow, graph, canvas, schedule, followup). No emoji, no multi-color icons (per platform convention).
- **Visual hierarchy** — action chips lead with the brand-orange accent border + orange icon; follow-up chips are neutral/secondary.
- **Accessibility** — chips are real `<button>`s activated by `click` (mouse + keyboard); `role="group"` + `aria-label` on the dock; per-chip `aria-label` ("Action: …" / "Ask: …"); `:focus-visible` rings; `aria-hidden` icons.
- **Motion** — staggered entrance (delay scales with chip index) + hover lift/glow; all disabled under `prefers-reduced-motion`.

## 16. Design Decisions

1. **Single seam at `run_agent_execution`, not per-engine** — the engines don't share a final-answer emit point; the service does. One hook covers all profile types + genie.
2. **Ephemeral dock outside `#chat-log`** — eliminates session-cache staleness, history pollution, and markdown re-parse at the root rather than guarding against them.
3. **Re-implement the editor's enablement truth** — instead of reusing `get_active_components` (wrong default + no governance), so chips are correct by construction and "no dead-ends" holds.
4. **Cost ladder, default-free** — value/cost is structurally enforced: A (free) → B (free) → C (opt-in, capped, async).
5. **Anti-fatigue as a feature** — cap, suppress-when-empty, auto-clear on next turn, per-user mute. In an enterprise product, "we don't bait you" is a real trust differentiator.
6. **Profile-scoped + per-turn** — suggestions follow `@TAG` overrides and reverts automatically at turn-completion time.
7. **Rebind, not regenerate** — to make the chips react to a profile change *without* a new turn (§12a), the recommender re-filters a **stored result-shape descriptor**, not the full result. This keeps the rebind 0-token (A+B only) and lets per-profile caching live exactly where the data genuinely *is* per-profile — the only place caching is meaningful.

## 18. Extending the Recommender

- **New action chip for a new component:** add an entry to `_ACTION_TEMPLATES` (`{label, prompt, icon}`) and a result-shape rule in `_build_action_chips`. Add the icon SVG to the `ICONS` map in `nextStepHandler.js`. Enablement is automatic via `_component_enabled_for_profile`.
- **New tier:** add a builder returning the chip shape `{id, kind, label, prompt, icon}`, slot it into `build_suggestions`'s ladder, and add a `tiers` keyword + config flag.
- **New config knob:** add to `DEFAULT_RECOMMENDER_CONFIG`, surface in the profile-editor "Smart Next Steps" card (`configurationHandler.js` load + save), document here.
